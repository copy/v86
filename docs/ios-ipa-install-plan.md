# iPhone 4 IPA 安装实施计划

状态：实施中。编写日期：2026-11-13。未在下方进度中验收的文件、API、协议和 UI 仍为计划。

目标机器为现有 `s5l8930`：iPhone 4 GSM（`iPhone3,1` / N90AP），iOS 6.1.3（10B329）。
基础能力与已有验收见 [iOS 使用说明](ios.md)和 [iPhone 4 实施计划](iphone4-plan.md)。

## 1. 交付目标

用户在 iPhone 控制台 UI 点击 **Install IPA…**，选择本地 `.ipa`，查看应用信息，点击安装。
模拟器检查兼容性、准备应用、传输文件，并通过客体原生安装服务完成安装。
成功后，应用出现在原版 SpringBoard 中，可以点击启动；冷启动后应用和存档仍然存在。

实施调整：在启动时预留专用的 128 KiB 信任节点区，安装前先持久保存新的启动清单，
暂停单核 A4 后追加不可变节点并最后发布链表头，随后继续原生安装。冷启动仍从完整清单重建。
该路径属于安装设备内部能力，UI 不调用调试内存 API；空间满时在传输前提示重启。

### 首版支持范围

- 用户本地提供的未加密 IPA，包含可在 Cortex-A8 上执行的 ARMv7 切片。
- 应用及必需的附带代码最低系统版本不高于 iOS 6.1.3，依赖的系统框架在该固件上存在。
- 主程序、资源、附带动态库的安装；安装时需要的临时空间检查、进度、错误报告和中断恢复。
- 先验证自行编译的 ad-hoc 签名应用，再扩展到需要本地重新签名的未加密 IPA。
- 浏览器主线程 CPU 和 CPU Worker 两种执行模式。
- 新建安装、同 Bundle ID 更新、重复安装处理；更新后保留应用原有数据。
- 现有虚机其他应用、设置和用户文件保持完整。

### 后续扩展

- UI 应用列表、卸载、批量安装和更大的持久信任容量。
- 更多旧应用的 Mach-O 布局、签名格式和 GLES 兼容性。
- 其他固件版本；每个版本单独建立经过验证的适配，不复用 10B329 的固定地址。

### 不包含

- FairPlay 解密、App Store 下载、Apple ID 登录和在线授权。
- 仅有 ARM64 或 ARMv7s 切片、要求更高 iOS 版本的应用。
- iTunes、USB 配对、AFC 或 `installation_proxy` 的完整模拟。
- 为个别游戏补全 Wi-Fi、Game Center、音频 PCM 等设备或服务。安装支持与运行兼容性分别记录。

## 2. 当前代码基础与缺口

| 位置 | 已有能力 | 本计划需要增加的内容 |
| --- | --- | --- |
| `src/android/zip.js` | ZIP 目录、流式解压、CRC 检查，IPSW 已复用 | IPA 包结构检查、权限等元数据、修改后的包重建 |
| `src/ios/plist.js` | XML plist 读取 | 通用二进制 plist 读取，不能把现有专用 binary plist 写入器当作读取器 |
| `src/apple/macho.js` | 单个小端 Mach-O、依赖、最低 iOS 版本读取 | Fat 切片、加密标记和更完整的边界检查 |
| `src/ios/guest_load.js` | GLES 依赖注入、签名页检查、指定 CDHash 信任缓存 | 通用应用准备、重签名、安装组件信任及可持续维护的应用信任清单 |
| `src/ios/system_volume.js` | 准备只读系统卷，安装 GLES 库并修改指定系统程序 | 安装助手、LaunchDaemon 及经验证的安装服务适配 |
| `src/ios/assemble.js`、`nand_boot.js` | 构建 NAND 并保存启动材料 | 保存安装能力版本、信任基线和持久安装状态所需的版本化数据 |
| `src/arm/backdoor_a32.js` | ARM 用户态与宿主的分块读写服务通道 | 独立安装服务及重连协议 |
| `src/arm/cpu.js` | 创建 GLES 后门设备 | 将安装通道与 GLES 插件、WebGPU 开关解耦 |
| `src/browser/starter.js`、`cpu_worker*.js` | 公共 API、Worker RPC 和事件 | 安装会话 API、流量控制、能力与进度事件 |
| `src/app/ui/console.js` | iPhone 控制台工具栏与操作 | `Install IPA…` 入口与安装对话框 |

现有 `V86.create_file()` 写入 9p 共享文件系统，不能用于写入 iPhone 的 NAND 数据卷。
现有 `link_guest_gles()` 要求 Mach-O 头部有足够空位，并要求签名满足其处理条件；它不是任意 IPA 的通用改写器。
现有 `graphics_kernel()` 校验原始内核指纹，并使用固定大小的空闲区域存放信任缓存；不能在安装时反复调用它
修改已经处理过的内核，也不能假定可以无限加入应用。

## 3. 整体方案

```text
iPhone 控制台：Install IPA…
    ↓
浏览器准备 Worker：检查 IPA → 选择 ARMv7 → 图形适配 → 重签名 → 生成清单
    ↓
V86 公共安装 API → ARM 后门中的独立安装服务
    ↓
iOS 安装助手：接收、校验、写入临时目录
    ↓
保存双份启动材料 → 暂停 A4、发布待安装代码信任 → 恢复执行
    ↓
MobileInstallationInstall → installd → 应用容器与系统注册
    ↓
确认安装结果、同步持久化 → SpringBoard 显示图标 → UI 显示 Installed
```

宿主负责包处理、安装控制和信任材料；客体负责文件写入与原生安装。
运行期间不从宿主直接修改已挂载的数据卷，避免绕过 HFS+、YAFTL、数据保护和客体缓存。

`MobileInstallationInstall()` 是优先验证的 iOS 6 路线。
[appinst 源码](https://github.com/akemin-dayo/AppSync/blob/master/appinst/appinst.m)提供了 iOS 5–7 的调用参考。
函数参数、调用身份、entitlements、安装回调和桌面通知行为仍须在本地 10B329 上验收。

## 4. UI 设计

### 入口

- 在 `src/app/ui/console.js` 的 iPhone 工具栏加入 **Install IPA…**，建议位于 Rotate 之后。
- 使用稳定选择器 `#iphone_install_ipa`，普通 PC、Linux、Android 控制台不显示。
- 它是运行时操作，不能只放进硬件设置页，也不依赖现有 9p Files 面板。
- 点击打开对话框；首版一次选择一个文件，文件选择器接受 `.ipa`，同时支持向对话框内拖放文件。
- 文件扩展名只用于筛选，实际接受与否以包内容检查为准。
- 窄屏按现有工具栏样式换行或收纳，入口仍可发现；具备键盘操作、焦点恢复和状态播报。

### 对话框流程

1. **Choose IPA**：说明当前支持 ARMv7、iOS 6.1.3 兼容、未加密应用。
2. **Checking IPA…**：读取文件，显示名称、Bundle ID、版本、最低 iOS、选中的架构和包大小。
   图标仅在可正确解码时预览，否则使用占位图标，不阻塞安装。
3. **Ready to install**：显示目标虚机。新应用按钮为 **Install**；相同 Bundle ID 为 **Update**，
   说明将保留现有应用数据，并显示新旧版本。降级需要额外明确选择，不能静默发生。
4. **Preparing / Transferring / Installing**：分别显示阶段与可获得的真实进度，不把上传百分比当作安装进度。
5. **Restart required**：若当前实现需要冷重启，在开始安装前说明；用户点击 Install 即授权流程完成必要重启，
   后续自动保存、重启和恢复，不逐步重复确认。
6. **Installed**：仅在原生安装成功、应用可查询且必要持久化已完成后显示；提示回到主屏点击应用图标。
   自动打开应用为后续功能。
7. **Failed / Interrupted**：显示可理解的原因和可复制的技术详情，提供适用的 Retry 或 Close。

普通用户流程不展示 CDHash、AMFI 地址、补丁偏移等实现细节。诊断信息通过可展开详情提供。

### 可用状态与取消

| 状态 | UI 行为 |
| --- | --- |
| 正在开机、等待助手握手 | 入口可打开；显示 Waiting for iPhone，允许检查文件，暂不提交安装 |
| 机器暂停 | 提示恢复运行后安装；不让上传一直等待 |
| 已就绪且无任务 | 可以安装 |
| 同一虚机已有任务 | 显示该任务进度，禁止创建第二个并行任务 |
| 助手或固件适配不匹配 | 显示能力不支持及升级办法，不显示虚假的可安装状态 |
| 机器关机或连接丢失 | 保留任务标识，显示等待重连或 Interrupted |

检查、准备和传输阶段可以 Cancel，清理未提交的文件。
进入原生安装提交后，只有验证系统支持安全取消时才提供取消；否则显示 Finishing installation。
关闭对话框不终止已提交任务，工具栏保留可重新打开的进度状态。
安装过程中暂停、重置、关机、挂起和加载快照等动作必须协调处理，不能破坏正在提交的任务。

  新增 **Open application**，通过鉴权助手调用 SpringBoardServices，仅允许持久清单中且代码身份获批的应用。
  该按钮报告原生启动请求结果；SpringBoard 尚未就绪时明确显示错误，不宣称应用已经运行。

  P0 的运行/存档及 P7 的完整持久化验收尚未完成。

### P0：先验证 10B329 的原生安装链路

1. 从用户本地固件中核对 MobileInstallation 接口、`installd` 的校验路径和可用系统依赖。
2. 编译最小 ARMv7 安装助手；借鉴现有 guest 构建脚本从本地 dyld cache 生成链接桩的做法。
   核对所需 entitlements 和运行身份，不假定 root 身份足以完成所有操作。
3. 用带已知 Bundle ID 的自制 UIKit 测试 IPA，调用原生安装接口，记录回调、返回值、容器路径和注册结果。
4. 分别定位安装校验失败、代码执行失败和图形失败，形成可重复的诊断方法。
5. 验证同 Bundle ID 更新、存档保留和 SpringBoard 图标刷新，确定是否需要额外的系统通知。

验收：在隔离测试 NAND 上完成一次真实安装和启动，明确安装服务与内核运行信任各自的要求。
此阶段可以在新测试数据卷中预置输入文件；正式产品流程不得靠重建数据卷安装应用。

### P1：IPA 检查与兼容性报告

建议新增 `src/ios/ipa.js`，扩展 `plist.js`、`src/apple/macho.js` 和必要的 ZIP 元数据读取。

1. 验证 ZIP 完整性，要求一个明确的 `Payload/<name>.app` 主应用。
2. 读取 XML / binary `Info.plist`，检查 Bundle ID、可执行文件、版本、设备类型及系统版本要求。
3. 检查主程序及必需附带 Mach-O；从 Fat 文件中选择兼容 ARMv7 切片，并核对实际依赖和最低版本。
4. 检查 `LC_ENCRYPTION_INFO`：缺少加密命令或 `cryptid == 0` 才进入后续准备；这只是包检查，
   不能把标记改为 0 当作解密。
5. 检查路径、重复条目、符号链接目标和资源上限；包不能借解压覆盖应用目录以外的文件。
6. 生成结构化报告，兼容性检查通过不等于承诺该游戏的所有功能均可运行。

验收：有效应用能报告元数据；ARM64-only、ARMv7s-only、加密、版本过高、损坏和结构歧义的包得到明确错误。

### P2：应用准备、图形适配与重签名

建议新增 `src/ios/ipa_prepare.js`、`src/ios/codesign.js`，复用并拆分 `guest_load.js` 中的通用能力。

1. 对用户 IPA 的工作副本进行修改，原始文件保持完整。
2. 为需要现有图形适配的主程序加入 `/usr/lib/libv86gles.dylib` 依赖，保持原有依赖 ordinal 和加载语义。
3. 首版支持经过验证、有足够头部空位的布局；无空位时给出具体错误。完整段偏移重排作为后续独立工作，
   不在未知布局上强行插入 load command。
4. 修改代码后生成 iOS 6 可接受的 ad-hoc 签名；处理相关 CodeDirectory、entitlements 和 bundle 资源封装。
   不能仅刷新几个页哈希就假定任意原始签名仍有效，也不能简单删除全部 entitlements。
5. 逐个处理附带代码，按正确顺序完成签名和包重建，保留安装需要的文件权限等元数据。
6. 完成所有修改后计算最终 CDHash，生成包摘要和安装清单；签名后不得继续修改代码。
7. 首先用 macOS 本地工具建立签名正确性的参考样本，最终浏览器 UI 路径须能独立完成首版支持范围的准备，
   不要求用户另外运行 `codesign` 或终端脚本。

验收：自制 UIKit 和 GLES 测试应用均能加载适配库；签名页、资源和附带代码校验通过。
准备过程采用流式读写或临时存储，避免在页面与 Worker 间反复复制整个大 IPA。

### P3：安装校验适配与持久信任

1. 将安装时 `installd` 的校验与启动时内核 / AMFI 的校验分开实现、分开测试。
2. 对 10B329 实际使用的签名校验入口实现最小适配；可以参考
   [AppSync 的机制说明](https://github.com/akemin-dayo/AppSync#im-a-developer--do-you-have-a-rough-high-level-explanation-as-to-how-this-all-works)，
   但须核对当前固件行为，不能把加载一个 dylib 当作已经完成函数拦截。
3. 安装适配只接受宿主当前提交且摘要匹配的应用；保留校验所需的签名信息，不能只把返回值改为成功。
4. 将安装助手、必要适配库、改过的系统程序以及应用所有必需代码纳入明确的信任清单。
5. 重构信任缓存构建：从经过验证的内核基线和完整清单重建，去重、排序，并在写入前检查容量。
   第一版允许明确拒绝超过容量的安装；扩大容量另行验证，不写越界。
6. 为后续冷启动保存可重复构建所需的基线、系统信任项、应用信任项和版本。
   确定 NAND 启动格式或配套本地数据的版本化编码，并验证现有导出、导入和擦除语义。
7. 采用专用预留区追加不可变信任节点；先落盘后发布链表头，单核 A4 暂停期间完成发布。
   旧节点在本次启动期间保留，避免破坏正在执行的 AMFI 查询；冷启动仅装载当前持久清单。
   静态清单上限为 189 个 CDHash，运行时区容量另行预检，两者均不得越界。

验收：新增应用与之前已安装的应用都能在冷启动后执行；信任缓存满、摘要不符或内核指纹不符时，
安装在修改现有应用前停止，原来的启动材料仍可用。

### P4：客体安装助手与控制通道

建议新增 `tools/ios/guest/app-agent.c`、构建脚本和 `src/ios/install_service.js`。

1. 通过 `system_volume.js` 准备助手、必要适配库和 LaunchDaemon，构建时加入对应信任项。
2. 助手在正常系统中启动，报告协议版本、固件、就绪状态和支持操作。
3. 复用 `BackdoorA32` 的 OPEN / READ / WRITE 服务机制，新增独立服务名，例如 `v86.ios.install`。
4. 在 `src/arm/cpu.js` 中将服务路由与 GLES 初始化解耦：关闭 WebGPU 时仍能连接安装助手，
   不为安装启动 shader 编译器；原有 GLES 服务行为保持兼容。
5. 协议包含版本、安装 ID、请求序号、总长度、偏移、摘要和有界分块；区分接收确认与安装结果。
6. 助手经客体文件接口写入受控临时目录，按任务记录接收状态，支持短读写、背压和重连。
7. 校验完文件才调用 `MobileInstallationInstall()`，把原生阶段、进度、错误及最终查询结果返回宿主。
8. 助手轮询无数据时让出 CPU，不能忙等；首次安装和更新均清理临时文件，并同步结果。

验收：大于单个传输块的包完整到达、摘要一致；GLES 开关和主线程 / Worker 组合均可通信。
重复请求不重复提交安装，陌生服务名和错误协议版本被明确拒绝。

### P5：公共 API、重启与任务恢复

新增安装 API 与事件，修改 `src/browser/starter.js`、`cpu_worker.js`、`cpu_worker_runtime.js` 和 `v86.d.ts`。
UI 只使用公共方法，不访问 `emulator.v86.cpu` 或直接改客体 RAM。

建议的 API 轮廓如下，具体参数在此阶段冻结：

```text
ios_install_status()                       能力、助手状态、当前任务
ios_install_begin(manifest)                创建任务，返回 install_id
ios_install_write(install_id, offset, data) 有界分块传输并确认
ios_install_commit(install_id)             提交准备好的任务
ios_install_cancel(install_id)             在允许阶段取消
ios-install-progress                       阶段、字节数、原生进度、结果
```

1. 实现主线程与 Worker 一致的行为、事件、错误和流量控制；高层编排放在新增 `src/app/ios_install.js`。
2. 原生安装前，助手将准备好的包和待安装任务同步到 NAND；宿主保留对应信任清单和任务摘要。
3. 若需要新信任项，助手先同步已验证的 IPA 与任务，然后暂停 A4。更新仅涉及 VSVFL 明确排除的
   原始固件分区，不能改写已挂载的数据卷；新载荷与提交头分别严格 flush 后，才发布运行时信任节点。
   `emulator.stop()` 只是暂停执行，不能等同于客体正常关机，也不用于绕过数据卷文件系统。
4. 启动材料更新采用可恢复的提交设计：保留上一份有效材料，验证新材料后再切换；
   启动材料与安装任务用同一代次标识，页面关闭或写入中断后可判断应恢复哪一份。
5. 信任发布后，助手核对同代次任务并调用原生安装；成功后宿主与客体共同提交结果。
   页面关闭后由启动清单、客体任务和原生查询决定恢复动作。
6. 助手失联时先按安装 ID 和 Bundle ID 查询真实结果，不直接重试原生安装。
7. 活跃安装期间不允许保存跨提交点的挂起状态。恢复已有快照时核对内存、NAND、任务及信任代次，
   不把新清单配给旧内存；包含完整一致状态的快照恢复按现有快照语义处理。

验收：发生必要冷重启后 UI 自动重新连接并继续任务；首次安装、更新、重试和刷新页面均不清空数据卷。

## 6. 任务状态与失败恢复

建议安装事务使用以下状态：

```text
checking → preparing → transferring → staged
         → restarting（需要新增启动信任时）
         → installing → verifying → installed

提交前可进入 cancelled；错误进入 failed 或 interrupted；重连后先查询再决定继续。
```

- 包摘要、准备后摘要和清单摘要区分保存，不能用原始 IPA 摘要描述已修改的内容。
- `install_id` 标识一次任务；Bundle ID 标识应用；更新产生新任务，但保留应用数据身份。
- 原生服务提交之前失败：清理临时包和未生效任务，不触碰已安装版本。
- 提交后断线：查询系统实际安装结果，再恢复任务或报告失败；不能假定系统会完整回滚。
- 更新失败：验证旧版本及数据是否仍完整；如系统不能保证回滚，先制定经验证的备份恢复方案再交付更新支持。
- 冷启动失败：恢复上一份有效启动材料，保留可诊断的任务状态；不能通过清空 NAND 处理安装错误。
- 每个阶段设定可诊断的超时；长时间安装有进度时允许继续，用户能看到当前阶段。
