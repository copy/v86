# x86-64

With `cpu_type: "x86_64"`, v86 presents an x86-64 CPU. A guest can use long
mode and compatibility mode, 4-level paging with NX, SYSCALL/SYSRET and
CMPXCHG16B, and a 36-bit physical address space. It can also use RAM beyond what
fits in the emulator's 32-bit WebAssembly memory. 64-bit code is compiled per
4 KiB page by the "page tier". Code in compatibility mode goes through the
existing 32-bit JIT.

| | |
| --- | --- |
| Option | `cpu_type: "x86_64"` (the default `"x86"` is the unchanged 32-bit CPU); index.html: CPU type |
| Verified guests | Alpine 3.24 x86_64 (Linux 6.18, the unmodified official ISO) on 1/2/4 cores, interpreted and with the page tier. Tested: 64-bit and 32-bit programs, threads, signals, TLB shootdown, virtio-net, snapshots, reboot, S5, S3/S4, 6.5 GiB of RAM. Windows 8.1 Pro x64 boots to the desktop on 1/2/4 cores and passes 64-bit and WOW64 probes. |
| Boot time | Alpine to login and through all probes: **1:16 / 1:52 / 2:08** (min:s) on 1/2/4 cores with the page tier, against about 16 / 85 / 140 minutes interpreted (debug build, 10-core Mac) |
| Not done | an optimizing region pipeline for 64-bit code (a deliberate decision, see below; the 32-bit one was deleted in M11 of [jit-unification-plan.md](jit-unification-plan.md)); running Windows interpreted (too slow); Windows S3/S4 |

## CPU profile

| Advertised | Not advertised |
| --- | --- |
| LM, NX, SYSCALL/SYSRET, LAHF/SAHF in long mode, CMPXCHG16B, RDTSCP, CLFLUSH, PAE, 4 KiB and 2 MiB pages, MMX, SSE–SSE3, POPCNT, RDRAND, the DE/MCE/MTRR/MCA/PAT bits that Windows x64 requires, `IA32_ARCH_CAPABILITIES` (RDCL_NO, MDS_NO, ...); 48-bit linear and 36-bit physical addresses (CPUID 0x80000008: EAX = 0x3024); with `cpu_features`, SSSE3, SSE4.1, SSE4.2, XSAVE, AVX, AVX2, FMA, F16C, BMI1, BMI2, LZCNT, MOVBE and the XSAVE family (below) | AVX-512, AES-NI, PCLMULQDQ, SHA, LA57, 1 GiB pages, PCID, VMX/SVM, x2APIC, TSC-deadline |

The option `cpu_features` adds SSSE3, SSE4.1 and SSE4.2 to either CPU type,
by name or as the preset `"x86-64-v2"`. With `cpu_type: "x86_64"` the CPU then
meets x86-64-v2 (RHEL 9, Windows 11 24H2 need it). It also adds XSAVE (the x87
and SSE state; CPUID.1:ECX.OSXSAVE follows CR4.OSXSAVE), AVX (which needs
XSAVE and SSE4.2, and adds the YMM state), AVX2, FMA, F16C, BMI1, BMI2, LZCNT
and MOVBE (with `cpu_type: "x86_64"` the preset `"x86-64-v3"`, what RHEL 10
needs; the 32-bit profile has these but LZCNT, whose encoding is BSR there),
and the XSAVE family XSAVEOPT, XSAVEC, XGETBV1 and XSAVES (Linux then saves
the state in the compacted format). With `cpu_type: "x86_64"` and no
`cpu_features`, the CPU has all of them (the owner's decision of 2026-10-17,
replacing [simd-xsave-plan.md](simd-xsave-plan.md) Q1's "off by default");
`cpu_features: []` gives the CPU without them, which `cpu_type: "x86"` keeps
by default. A snapshot keeps the CPU its guest saw: a machine whose
`cpu_features` was not given restores a snapshot with other features and
takes them, one given `cpu_features` refuses it. The contract
records them as the profiles `legacy-v2`, `x64-v2`, `legacy-xsave`,
`x64-xsave`, `legacy-avx`, `x64-avx`, `legacy-v3`, `x64-v3`, `legacy-xsaves`
and `x64-xsaves`; `tools/release_gate.mjs --levels R-SSE4`, `R-XSAVE`,
`R-AVX`, `R-x86-64-v3` and `R-XSAVE-ext` run their acceptance. `make
x64-glibc-tests` runs Alpine x86_64 with glibc 2.39's x86-64-v3 code (ld.so's
levels, glibc-hwcaps, the IFUNC choices and their results, against QEMU) and
checks the YMM registers across context switches, signals and migrations.

The CPU identity is pinned as data. `node tools/cpu_contract.mjs` records the
CPUID leaves and 47 MSRs of the running emulator into
[`tests/platform/cpu-contract.json`](../tests/platform/cpu-contract.json), for
the profiles `legacy-1`, `legacy-4`, `x64-1`, `x64-4` and the ten above.
`make platform-contract-tests` fails on any change that is not also recorded
there. Unknown MSRs raise #GP in the x64 profile, which is what 64-bit kernels
expect when they probe with `rdmsr_safe`. The legacy profile keeps upstream's
behaviour of reading them as 0, and so does the x64 profile with EFER.LME clear.
The x64 profile's own MSRs (`IA32_ARCH_CAPABILITIES`, KERNEL_GS_BASE, TSC_AUX,
...) are there in every mode, so a 32-bit kernel on `cpu_type: "x86_64"` reads
them too ([`tests/x64/protected_mode_msrs.mjs`](../tests/x64/protected_mode_msrs.mjs)).

## Design

**The emulator stays wasm32; only the guest becomes 64-bit.** WebAssembly
already has `i64`, so 64-bit guest registers do not need Memory64. v86 keeps
four kinds of address apart, as separate types: `GuestIp` (u64), `LinearAddress`
(u64, checked for canonical form after segmentation), `PhysicalAddress` (u64,
at most 36 bits) and `HostOffset` (u32, an offset into the WebAssembly memory).
A guest address is never used directly as a host offset, and the high bits of a
64-bit value are never dropped through `Number`, `|0` or `>>>0` in JS.

**The wider state extends the existing layout.** [`gen/state_layout.js`](../gen/state_layout.js)
generates the state offsets for Rust and JS. The 16 × 64-bit GPRs are split into
banks: the first 8 registers keep their low dword at the old addresses, so the
32-bit interpreter and JIT did not have to change, and new banks hold the high
dwords and R8–R15. The layout also adds 16 XMM registers, 64-bit
RIP/CR/DR/descriptor-table bases, and the new MSRs, for 1936 bytes per core in total. In
64-bit mode, a 32-bit write zero-extends into the full register, and 8-bit and
16-bit writes keep the other bits.

**CPU modes are explicit.** There are seven modes: Real, VM86, Protected16,
Protected32, Compatibility16, Compatibility32 and Long64. The current mode comes
from CR0.PE, EFLAGS.VM, EFER.LMA, CS.L and CS.D. Operand, address and stack sizes
are decided separately from CPL.

**The 32-bit engine stays as it was; long mode has its own engine.** Code with
EFER.LMA = 0 runs on the unchanged 32-bit interpreter and IR. With LMA = 1, the
x64 engine in [`src/rust/x64/`](../src/rust/x64/) takes over. After the x64 work
first landed, 32-bit boot time grew to 1.148× the old baseline, over the 10%
budget. Moving the new long-mode branches out of the hot 32-bit helpers brought
it back to 1.095×.

**One decoder serves both the interpreter and the compiler.** `decode_with`
fetches instruction bytes through a callback and never touches data memory, so
decoding for the compiler cannot trigger MMIO or guest exceptions. It covers
REX ordering, the AH/SPL byte register aliasing, RIP-relative addressing,
moffs64, imm64, the 15-byte limit, and the order of #UD and fetch faults. It was
checked against the independent iced-x86 decoder on the whole long-mode opcode
map (349,888 encodings) and on 33,088 address forms.

**The MMU keeps a bounded TLB.** The page walk has four levels, supports 4 KiB
and 2 MiB pages, and checks NX, U/S, R/W, CR0.WP, A/D bits and reserved bits
above bit 35. The 64-bit TLB is tagged with the full linear page, the access
type and an epoch, with separate slots for reads, writes and fetches. There is
no direct-mapped array indexed by the 48-bit page number.

**System behaviour follows the Intel SDM.** This covers the long-mode IDT, the
64-bit TSS with RSPn and IST, IRETQ, 64-bit call gates and far JMP/CALL, NMI
blocking, #DF and triple fault (a machine reset), SYSCALL/SYSRET/SWAPGS, and
SYSENTER/SYSEXIT from compatibility mode. As on Intel CPUs, SYSCALL in
compatibility mode raises #UD. The MSRs FS/GS/KERNEL_GS_BASE, STAR/LSTAR/SFMASK,
TSC_AUX, PAT, the MTRRs and the MCA banks are implemented, and CR8 is an alias
of the APIC TPR.

**Interrupts arrive at instruction boundaries.** Some device callbacks raise an
IRQ synchronously, for example an IDE data port read or an 8042 write. If such
an IRQ were delivered in the middle of a 64-bit instruction, the instruction's
final RIP update would overwrite the interrupt handler's RIP. The x64 engine
therefore holds external interrupts until the instruction has committed or
faulted. The 32-bit path keeps delivering them immediately, as before.

**The x64 JIT is a page tier, not a wider region pipeline.**
[`pagegen.rs`](../src/rust/x64/pagegen.rs), [`pages.rs`](../src/rust/x64/pages.rs)
and [`jac.rs`](../src/rust/x64/jac.rs) compile one WebAssembly function per 4 KiB
page of long-mode code:

- Functions are keyed by the backing physical page and do not depend on where
  the page is mapped, so a shared library can reuse the same function in every
  process, even with ASLR.
- The GPRs live in i64 locals. EFLAGS are recorded lazily and only computed
  when something reads them.
- Common integer, stack, control-flow, string, atomic and SSE instructions
  (moves, logic, ADD/SUB/MUL/DIV in PS/PD/SS/SD forms, COMISS/UCOMISS, the
  SSE2 packed-integer, shuffle and shift forms, the scalar conversions,
  LDMXCSR/STMXCSR), INVLPG and MOV from CR0/CR2/CR3/CR4 are compiled from
  templates. The packed conversions (CVTPS2PD, CVTPD2PS, CVTDQ2PS, CVTDQ2PD,
  CVT(T)PS2DQ, CVT(T)PD2DQ) use the templates Tier-0 shares
  (`x86tpl::ops`, [jit-unification-plan.md](jit-unification-plan.md) P2.5;
  the JIT switch `x64_cvt`, on by default, turns them back into steps). Any other instruction
  is executed by the interpreter from inside the function ("step in place"),
  and so is an instruction that continues into the next page.
- If a memory access cannot complete inside the function, the function exits
  with RETRY and the interpreter runs that instruction from the start. The
  function has made no change yet at that point. This covers faults, MMIO,
  and writes to pages that contain compiled code. An access that crosses into
  the next page is served when both pages are plain RAM with adjacent backings
  (`pages::crossing_host`; guest RAM is one array, so most are), and for a
  write neither page has compiled code; else it retries too (always with
  cores in workers, whose atomic accesses need alignment).
- `jac.rs` is an access cache per core × read/write × CPL0/CPL3, looked up by
  one small internal function of each module. It also maps the VGA linear
  frame buffer: a write translation marks its page dirty when it is filled and
  is retired after the next screen update. INVLPG retires one page's entries
  (a 2 MiB region's when large pages were cached there); MOV CR3 with
  CR4.PGE keeps the entries of global translations, as the TLB does.
- A function leaving its page continues in the next page's function with a
  Wasm tail call when the chaining table (`pages.rs` `CHAIN`, per core and
  CPL, tagged like the access cache) has it; otherwise it returns to the
  dispatch loop. Engines without tail calls always return. With cores in
  workers, a chain also returns when other cores published or invalidated
  code.
- Dispatch inside a function uses a 256-entry table of 16-byte buckets and
  compares. An entry the function does not serve is stepped in place up to
  the next block start; repeated such entries trigger a recompile, which also
  serves the offsets seen once so far. Straight-line continuations are no
  entries: after a retried instruction the dispatch loop interprets up to an
  offset the function serves (`pages::unserved_run`). Likely function starts
  (16-byte aligned after INT3 padding) are compiled as block starts from the
  first compile, unless decoded code runs into them (the 0xCC was an
  instruction's last byte, `pagegen::GUESSED`).
- An instruction that continues into the next page runs natively while that
  page fetches as the bytes it was compiled with (`x64_page_straddle`, one
  word compared), else it is stepped. Windows has hot loops across page
  boundaries (ci.dll's big-number arithmetic among them).
- A page is compiled after 2000 of its instructions have been interpreted. At
  most 9000 functions are live. After four compiles of a page, each further
  one waits for twice as many interpreted instructions or unserved entries.
- Code outside compiled code (docs/jit-unification-plan.md P4.5): whether the
  IR scheduler compiles is an atomic flag, not a lock; a page without a
  function counts its interpreted instructions in a batch (`HeatBatch`,
  `x64_heat_batch`), so the next miss there skips the function and page
  lookups; and after a cold miss the interpreter runs on along the page
  (`x64_miss_run`, at most 64 instructions, stopping at another page, an
  unchanged RIP, a mode or CPL change or a core event; far transfers within
  the page are noted as entries). A cold instruction costs about 58 ns
  instead of 76.
- STI and the instruction in its interrupt shadow compile into one block,
  which then checks for a deliverable interrupt (`x64_sti_shadow`; P4.5d).
  Before, STI left the function and the shadow instruction ran in the
  interpreter: about 96 ns for an STI/NOP/CLI window, now 8. Windows 8.1's
  boot executes about 7 million of them (system calls enable interrupts with
  STI).
- SSE arithmetic (ADD/SUB/MUL/DIV/SQRT/MIN/MAX/RCP/RSQRT in PS/PD/SS/SD forms)
  uses the templates Tier-0 shares (`x86tpl::ops::float`;
  `x64_sse_fast_check`, docs/jit-unification-plan.md P4.18): with MXCSR.PE
  set a native result needs no exactness check; with PE clear the template
  finds an inexact result itself (TwoSum; single precision in double;
  Dekker's product for double MUL/DIV within 2^±450) and sets PE. A refused
  instruction runs the exact helper (`x64_sse_fp`) in place, as IR Tier-0 did.
  MXCSR's condition and the SSE availability check are evaluated once per
  block, and registers known to hold no NaN or denormal skip their operand
  checks.
- Code quality for hot code (P4.14–P4.17, P4.20–P4.23; on since M5, each
  switch kept as a fallback):
  - A page whose function ran its blocks about four million times
    (`x64_hot_count`, 2^22 entries and dispatches, counted per function) is
    recompiled with inline access cache lookups (`x64_hot_inline`). Cold
    compiles keep calling the module's lookup function, which keeps Windows'
    boot compiling fast. A hot recompile costs V8 about 2.6 times what the
    cold compile did (TurboFan, in the background), and the new function
    starts over as Liftoff code while V8 had already optimized the old one;
    at 4096 Windows 8.1's boot had run 28% fewer instructions after 150 s.
  - The access cache has 2048 entries per table (`x64_jac_entries`), which
    halves the fills of a Windows boot.
  - Loops of the block graph are Wasm loops whose back edges skip the page
    dispatch (`x64_loops`), in the hot recompiles only (`x64_loops=2`): in
    every compile they cost TurboFan an eighth more time, and during a
    Windows boot V8's background compiles are what limits how soon the
    page functions leave Liftoff code.
  - Within a block, XMM registers live in v128 locals (`x64_xmm_locals`),
    scalar moves and results merging by shuffles and VEX.256 forms keeping
    their low halves there (bits 255:128 in memory).
  - 32-bit integer operations compute in i32, and CMOV is a `select`
    (`x64_i32_ops`). A 32-bit ADD was five ARM64 instructions under V8, the
    masks of the 64-bit form included; now it is one.
  - Inline lookups compare the tag of the operand's last byte, so a page
    crossing misses without an offset compare, and add the entry's host
    delta (`x64_fast_lookup`). Per base register, kind and displacement page
    (displacements within 2 KiB of 0 share one: a frame's or a structure's
    fields), the translation of a `[register + displacement]` operand or a
    stack operation is kept while the function runs (for an operand whose
    first and last bytes are both in its page); INVLPG and single steps forget
    it. In compatibility mode it is kept within a block (its first access
    there sets it on every path): kept across loops and dispatch, it took
    registers that cost more than the lookups it saved.
  - Chaining can pass the GPRs to the next page's function in a contiguous
    buffer (`x64_fast_chain`, off: no benchmark measured a difference).
  - Shifts, rotates and MUL/IMUL compute only the EFLAGS bits that are read,
    or that a way out of the function could observe, before something writes
    them again (`x64_exit_flags`).
  Modules are kept small (Windows boots compile 10–30 thousand of them;
  engines compile about 30 MB/s of them lazily on the first call).

The 32-bit region pipeline (HIR, MIR, StateMap and the proofs behind each
optimisation) was built around 32-bit registers and flags. Widening it would
have taken as much work as writing the page tier did, and the page tier already
boots Linux in 1–2 minutes. Profiles of Windows show that the remaining time
goes to instruction classes that have no template yet, not to missing
optimisations across blocks. So there was deliberately no x64 region pipeline;
since M11 deleted the 32-bit one, the page tier is the only compiler
([ir-design.md](ir-design.md)), and long-mode code uses it even with
`ir_tier0: false`.

**Compatibility-mode code goes through the page tier, else the interpreter.**
Code of WOW64 and i386 processes runs with LMA = 1 and CS.L = 0. The page tier
compiles it (`x64_page_compat32`, below); without it (`ir_tier0: false`, or
the switch off) it is interpreted (the 32-bit region tiers compiled it,
`x64_compat_jit`, until [jit-unification-plan.md](jit-unification-plan.md) M11
deleted them; IR Tier-0 until P7.5). x64 translations of its 32-bit linear addresses are placed in the
legacy TLB (`fill_ia32e_tlb`, RAM only); entries made by data accesses carry
`TLB_IA32E_DATA`. In compatibility mode, compiled code, the interpreter and the
dispatchers all use these entries:

- `translate_address`, `safe_read*`/`safe_write*` and read-modify-write
  instructions look in the 32-bit TLB first (`ia32e_compat_backing`) and take
  the x64 translation only on a miss or a refused entry.
- Instruction fetch (`get_phys_eip`, `read_imm*`) caches the fetch page
  (`last_virt_eip`/`eip_phys`) as legacy mode does.
- Instruction fetch, compiled-code lookups and code snapshots use only entries
  that a fetch made (without `TLB_IA32E_DATA`), so execute permission and NX
  were checked.

**The page tier runs compatibility-mode code** (the JIT switch
`x64_page_compat32`, on by default since M9 passed its D gate,
[jit-unification-plan.md](jit-unification-plan.md) P7.2; the same code as
legacy protected mode's, `x64_page_legacy32`, P7.3). Its functions are
keyed by physical page and code mode (`COMPAT_KEY`): a page run as 64-bit and
as 32-bit code has a function for each. A function runs only while the code is
plain WOW64 code (`pages::compat_runnable`): a 32-bit CS and stack, and CS, DS,
ES and SS with base 0 (FS and GS bases are added at each access); a step that
changes that leaves. Generated code reads and writes the GPRs' low halves only
(WOW64 keeps the high halves), wraps EIP, ESP and addresses at 4 GiB, uses
4-byte stack slots, and steps, retries and leaves cold code to the 32-bit
interpreter. Memory operands look up the 32-bit TLB above, as IR Tier-0 did
(`x64_compat_tlb`; x64 translations fill it in compatibility mode while the
switch is on). Where the SDM leaves EFLAGS undefined, the results are the
32-bit interpreter's: its lazy record gives AF of multiplies and shifts from
`last_op1`, and SF, PF, AF and OF after BSF/BSR and SHLD/SHRD; the page tier
keeps those pending as an addition of `last_op1` and result − `last_op1`
(`pagegen::Emitter::legacy_record`). x87 (fast math, with the f64 shadow cache
and register-only runs, `x86tpl::x87run`), MMX, SSE/AVX, BMI and the
bit scans have templates; the rest steps. `tests/x64/compat_jit.mjs` and
`tests/x64/compat_fuzz.mjs` (`make x64-wow64-tests`) compare it with the
interpreter.

(Until P7.5, IR Tier-0 queued compatibility-mode pages with their CR3, CPL and
state flags, and `x64_long_visit`, P4.6, compiled one from a frame that started
in 64-bit code: WOW64 code whose compile was due otherwise waited for a frame
with a compatibility-mode slice, 1.4% of 3DMark06's frames in game test 2. The
page tier compiles where the code runs.)

64-bit code never uses the 32-bit TLB. x64 INVLPG and MOV CR3 flush these
entries; MOV CR3 with CR4.PGE (and no PCID) keeps global ones. MOV to CR0 or CR4
flushes only when it changes a bit translations depend on (CR0.PE, WP, PG;
CR4.PSE, PAE, PGE) or EFER, as on hardware. When only compiled code used these
entries, the interpreter, the dispatchers and the runtime took the full x64
translation on every fetch and data access of WOW64 code. In 3DMark06 on Windows
8.1 that was 4–10 million TLB refills a second and about 19% of host time,
against about 300,000 refills and 1–2% with it (measured 2026-10-02; frame rates
in [GPU devices](gpu-devices.md#performance)). The CR0/CR4 rule gained nothing
measurable there: Windows 8.1 does not write CR0, and its CR4 writes all flip
PGE for a global flush, which must clear the TLB anyway.

**The physical bus is 36 bits wide.** [`physical.rs`](../src/rust/x64/physical.rs)
maps up to 16 page-aligned windows of RAM or MMIO. Every change to the windows
bumps a generation counter, so no stale mapping can survive. The testing option
`high_memory_size` moves the top of `memory_size` up to 4 GiB. CMOS registers
0x5B–0x5D report it, and SeaBIOS turns that into an E820 entry. Devices keep
their real address widths, but all of them go through the bus. VirtIO and v86gl
use 64-bit descriptors. IDE bus-master DMA (the PRDT) and 8237 ISA DMA stay
limited to 32 bits. IDE 48-bit LBA addressing was fixed.

**Extended RAM goes beyond the wasm32 limit.** Memory64 and multiple memories
were considered and rejected: both would require rewriting the whole CPU core,
and browser support for Memory64 is uneven. Instead, `extended_memory_size`
adds RAM at 4 GiB + `high_memory_size`, stored outside the WebAssembly memory
([`src/rust/extended.rs`](../src/rust/extended.rs), the engine the arm64 core
shares, with x86's part in [`src/rust/x64/extended.rs`](../src/rust/x64/extended.rs):
the aperture, the access cache's frames, LOCK operands;
[`src/extended_memory.js`](../src/extended_memory.js)):

- The pages are kept in host ArrayBuffers, which are SharedArrayBuffers when
  available so that vCPU workers can share them. The buffers are allocated
  lazily in 1 GiB chunks, and a bitmap records which pages have been written.
- A frame pool in the WebAssembly heap (512 MiB by default) caches pages. When
  it is full, pages are evicted with a second-chance ("clock") policy.
- The interpreter looks up the frame on every access. The page tier's access
  cache can hold frames, marked CACHED, which are released at safe points.
- The page tier compiles code in extended RAM as it does code in RAM. Such a
  function is keyed by the extended page, not by its frame, so it outlives
  the frame's eviction. Every write to the page (by the interpreter, DMA or a
  string instruction) retires the function, and the access cache never gets a
  write entry for the page. With cores in workers, code in extended RAM is
  interpreted, because their writes are not tracked.
- Compatibility-mode code reaches extended RAM through a 1 MiB aperture at
  0xFED00000.
- A LOCK read-modify-write on extended RAM holds a lock until the instruction
  ends.

**Snapshots can be streamed.** Machines with more than 200 MB of state are
saved and restored through `save_state_stream`/`restore_state_stream`, the V7
format of checked records of at most 1 MiB. Neither side ever needs the whole
state in one buffer. Extended RAM is saved only in V7 streams. V6 snapshots
still load.

**Boot through the BIOS or with a bzImage.** An x86_64 kernel can be started
with `bzimage` + `initrd`: v86 loads it through the 32-bit Linux boot protocol,
and the kernel enters long mode on its own. Booting from a disk or ISO through
SeaBIOS works as usual. The multiboot loader rejects 64-bit ELF files outright,
instead of misreading them as 32-bit files.

```text
               | low RAM: memory_size - high_memory_size      |  (VGA hole at 0xA0000)
               +----------------------------------------------+
               | PCI MMIO window                              |  from the first 256 MiB
               |                                              |  boundary above RAM
0x0_FEC0_0000  | IOAPIC                                       |
0x0_FED0_0000  | aperture into extended RAM (1 MiB, x64 only) |
0x0_FEE0_0000  | LAPIC                                        |
0x1_0000_0000  +----------------------------------------------+  4 GiB
               | high RAM: high_memory_size                   |  (moved from the top of
               +----------------------------------------------+   memory_size)
               | extended RAM: extended_memory_size           |  (host-backed)
               +----------------------------------------------+
0xF_FFFF_FFFF  end of the 36-bit physical address space
```

### One page-tier function

```text
4 KiB long-mode code page (backing physical page P)  ==>  WebAssembly function f_P(entry)

  entry guard: CPL, CS, mode, CR0/CR3/CR4, EFER, IF/TF/AC/RF/IOPL, DR7, cache epoch
  br_table on the offset in the page
     |
     v
  block --> block --> block ...        (GPRs in i64 locals, EFLAGS recorded lazily)
     |  template instruction:  jac lookup inline -> host address -> load/store
     |  other instruction:     write state back -> x64_page_step() -> reload locals
     v
  exit NORMAL   RIP written, continue in the main loop
  exit RETRY    the instruction had no effect yet: the interpreter runs it
                (page fault, MMIO, a write to a page with compiled code,
                 a crossing into a page whose backing is not adjacent)
  exit UNKNOWN  new entry offset: record it, recompile the page later

  code write to P (CPU, DMA, host) -> jit_dirty_page -> retire f_P on every core
```

## Example

**Windows 8.1 x64**, in the style of the image in `retro-gaming-site/windows8/`:

```js
emulator = new V86({
    graphics_adapter: "bochs_vga",
    wasm_path: "v86.wasm",
    memory_size: 2 * 1024 * 1024 * 1024,   // clamped to 2 GiB - 128 KiB (wasm32 limit)
    vram_size: 16 * 1024 * 1024,
    bios: { url: "bios/seabios.bin" },
    vga_bios: { url: "bios/vgabios.bin" },

    hda: { url: "windows8/windows8.img", async: true, size: WINDOWS8_IMAGE_BYTES },
    acpi: true,                // Windows x64 needs ACPI and the APICs
    cpu_type: "x86_64",        // advertise long mode, NX, SYSCALL, CMPXCHG16B, ...
    net_device: { type: "ne2k", relay_url: "wss://relay.widgetry.org/" },
    autostart: true,
});
```

**More RAM than wasm32 can hold** (for a 64-bit guest only):

```js
    memory_size: 512 * 1024 * 1024,                 // in the WebAssembly memory
    extended_memory_size: 6 * 1024 * 1024 * 1024,   // 6 GiB more at 4 GiB and above, host-backed
    // extended_memory_cache: 512 * 1024 * 1024,    // frame pool in the wasm heap (default)
    // high_memory_size: 128 * 1024 * 1024,         // testing: move part of memory_size above 4 GiB
    cpu_type: "x86_64",
```

Save such a machine with `save_state_stream(chunk => ...)`; the single-buffer
`save_state()` refuses when extended RAM holds data (pages written only in
their frames included: it writes them back first). If the host cannot allocate
the extended RAM, `new V86` fails at startup. The size is limited by the 36-bit
physical address space and by host memory.

`index.html` does this split itself: a Memory size above 2048 MB puts 2048 MB
in `memory_size`, the rest in `extended_memory_size` (at most 63488 MB in all),
selects the x86_64 CPU type (arm64 keeps its type: up to 1792 MB in its Wasm
heap, see [virt.md](virt.md)), and saves such a machine as a V7 stream. Linux hands
out the highest pages first, so much of a guest's memory, its programs
included, is extended RAM. The Alpine x86_64 boot test on one core takes about
as long with 2048 + 2048 MB as with 2048 MB (47–55 s against 41–44 s).

On more than one core, add `cpu_cores` and `experimental_smp_jit`; see
[multicore.md](multicore.md). The page tier is on by default. `disable_jit: true`
runs 64-bit code interpreted, roughly 12 times slower.

**Known limits:**

- Some instructions have no page-tier template yet and run one at a time
  through the interpreter: x87, MMX, FXSAVE and
  FXRSTOR, SYSCALL/SYSRET, IRETQ, port I/O and MOV to CR3. Windows 8.1 on one core averages about 180 MIPS during boot;
  see `tests/x64/windows_boot.mjs` (WIN_STOP_AT_DESKTOP, WIN_CPU_PROFILE,
  WIN_OVERLAY_SAVE/LOAD) for boot timing.
- 32-bit PAE guests cannot use page table entries above 4 GiB.
- Extended RAM always takes the slow path when cores run in parallel, and
  code there is interpreted.
- One 4-core Alpine run once stopped after `poweroff` without reaching S5, on an
  idle host. It has not happened again in 12+ runs, and its cause is unknown.
  Later "hangs" on a heavily loaded host turned out to be shutdown scripts that
  took longer than the 120 s timeout.
- `cpu_type: "x86_64"` stays opt-in and is not advertised to guests by default.
